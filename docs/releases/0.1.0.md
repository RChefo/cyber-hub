# Cyber Hub 0.1.0

Cyber Hub is a local-first workstation for authorized security assessments. Projects keep their authorized scope, findings, evidence, tool runs and reports together, and every tool that sends traffic is checked against that scope before it runs. Your data is stored only on your computer. Online features (threat-intelligence, OSINT and vulnerability-score lookups, the project assistant) contact their services when you use them; the automatic update check is on by default and can be turned off in *Settings → Updates*.

## Highlights

- **Projects with an authorized scope:** domains, wildcards, addresses, networks (CIDR) and URL entries, with exclusions. Tool runs, imports, discovery and MCP requests are checked against it. Refused operations that would contact a target (HTTP requests, TLS analyses, web-service checks and service scans, also from workflows) are kept in the scope history.
- **Engagement workspace:** engagement details (client, engagement type, authorization reference, objectives, methodology, contacts), a scope manager that tests targets without contacting them, the evidence vault and a project timeline.
- **Findings:** a lifecycle with history, CVSS 4.0 and 3.1 vectors scored as in FIRST's calculators, a finding library with templates, and bulk editing. Findings export as CSV, JSON or SARIF 2.1.0; SARIF files go to GitHub code scanning and other tools with a security severity, a location and a stable fingerprint per finding, and false positives arrive as suppressed results. The MITRE ATT&CK techniques the findings name (from the log, file and Linux triage and Prowler imports) export as an ATT&CK Navigator layer, colored by severity.
- **Imports:** Nmap, Nuclei, Nessus, Greenbone/OpenVAS, Burp Suite, OWASP ZAP and SARIF results, Prowler cloud audits (OCSF JSON for AWS, Azure, Google Cloud and Kubernetes) and CSV files with a column mapping. Imports deduplicate, check the scope and verify fixes by rescan; a Prowler rescan resolves the findings whose checks now pass. Suppressed SARIF results (dismissed in the source or in another tool) and muted Prowler findings are skipped. CVEs can optionally be tracked as vulnerabilities.
- **API security:** OpenAPI 3.x and Swagger 2.0 definitions (JSON or YAML), Postman collections and HAR captures become a per-project endpoint inventory with the scope status of every endpoint. Checks mapped to the OWASP API Security Top 10 (2023) report anonymous write operations, Basic authentication, API keys and secrets in URLs, deprecated OAuth flows, cleartext and non-production servers, unbounded page sizes and deprecated operations; a test plan lists the endpoints to test for object- and function-level authorization, mass assignment, SSRF and rate limits. Issues can be recorded as findings, and an endpoint opens in the HTTP request builder. Only names are kept, never tokens or values. Two imports of the same API can be compared: endpoints added, removed and changed, with endpoints that lost their authentication, new anonymous endpoints and new plain-HTTP servers reported.
- **SBOM and lockfile analysis:** dependency lockfiles (npm, Yarn, pnpm, Cargo, Poetry, uv, Pipfile, pinned requirements.txt, Composer, Bundler, go.mod, NuGet, Gradle) are read like SBOMs, with supply-chain checks for plain-HTTP downloads, missing integrity hashes, Git and URL dependencies, several registries and pip's `--extra-index-url`. CycloneDX (JSON, XML) and SPDX 2.x (JSON, tag-value) SBOMs per project, with each component's license risk, the SBOM's completeness against the NTIA minimum elements, the vulnerabilities the SBOM states (with VEX analysis), and an optional check on OSV.dev that sends package URLs only. Each vulnerability of a component can be recorded as a finding with its CVE, severity, CVSS vector and fixed versions. Two SBOMs or lockfiles of the software can be compared: components added, removed, upgraded and downgraded, vulnerabilities that came or went, and supply-chain warnings for packages that now come from another source, the same version with other content, downgrades and stricter licenses.
- **Container and Kubernetes checks:** Dockerfiles, Compose files and Kubernetes manifests, pasted or read from a file or a whole folder, are checked offline against the Kubernetes Pod Security Standards (baseline and restricted) and the CIS Docker Benchmark: root users, privileged containers, host namespaces and mounts, the runtime socket, capabilities, disabled seccomp, secrets in the files, unpinned images, exposed databases and more. RBAC roles are checked for the escalation paths in the Kubernetes RBAC good practices (escalate, bind, impersonate, nodes/proxy, token and certificate issuing, webhooks, wildcards), and bindings are followed across files to report dangerous rights given to anonymous users, all users, all service accounts or a default service account. Issues can be recorded as findings.
- **Cloud and infrastructure-as-code checks:** Terraform (HCL, JSON and plans), CloudFormation and AWS IAM policies, including the export of a whole account's IAM, are checked offline for public buckets, open security groups, public or unencrypted databases, IMDSv1, disabled CloudTrail, administrator access, the IAM privilege-escalation methods catalogued by Rhino Security Labs, and roles that anyone, any GitHub repository or an account without an external ID can assume. Issues can be recorded as findings.
- **File triage:** Windows and Linux programs (PE, ELF) are examined without being run: hashes and the import hash, sections and their entropy, packers, hardening flags, capabilities inferred from the imported functions with their MITRE ATT&CK technique, and strings with the indicators found in them. Hashes go to the VirusTotal or Threat Intel page on request.
- **Linux persistence triage:** a mounted image or a triage collection (such as UAC's) is read without running or changing anything, and without following links out of it: cron, systemd services and timers, boot scripts, preloaded libraries, shell start-up files, SSH keys, accounts, sudo, PAM, desktop autostart and udev rules are checked for downloads piped into shells, reverse shells, miners, hidden programs and risky settings, each with its MITRE ATT&CK technique and the file's SHA-256; services, keys and jobs added on the host are listed for review.
- **Packet capture and log triage:** pcap and pcapng files are summarized offline (hosts, conversations, DNS, HTTP, TLS server names) and cleartext logins are reported without their passwords; web access logs and SSH authentication logs are searched for injection attempts, Log4Shell, sensitive files that were served, scans and password guessing. Windows event logs (EVTX) are read without Windows tools and checked by 35 detections, mapped to MITRE ATT&CK techniques where one fits: cleared logs, password spraying, new administrators, services and tasks that run commands, encoded PowerShell, credential dumping, DCSync, Kerberoasting and more. Results can be recorded as findings.
- **Attack surface management:** passive discovery (certificate transparency and DNS), web-service checks and service scans fill the asset inventory. A subdomain monitor reports new and missing names across passive runs.
- **Vulnerability management:** CVEs per project or asset, with the CISA KEV flag, optional EPSS scores from FIRST.org and a priority that shows each factor.
- **Workflow automation:** projects chain predefined steps (passive discovery, web-service checks, service scans, score updates, saved reports). Steps that contact targets need a confirmation and pass the scope check again when they run. Workflows with passive steps only can run on a schedule while Cyber Hub is open.
- **Investigation:** the *Investigation* tab of a project connects the results of the modules. *Correlate* suggests relationships between findings, assets, vulnerabilities, evidence, OSINT entities, API endpoints and SBOM components from exact matches (the same URL, host, CVE, package URL, file hash or API path), each with its reason, the fields that matched and a confidence. Suggestions stay suggestions until you accept, reject or dismiss them; accepting one between a finding and another record creates the finding link that reports use, and every decision is kept on the timeline. Any record opens a panel with everything related to it and how that is known. Records can be linked by hand, including to ATT&CK techniques. The investigation graph shows the relationships with their origin and verification, finds the neighbourhood of a record and the shortest chain between two, and exports as JSON, SVG or PNG. The timeline can be limited to one record, to words and to dates and exported as CSV or JSON, and evidence records show where they came from (module, record, tool, collection time) and the result of their last integrity check. Findings from file, packet capture, log and event log triage are recorded together with the analysed file and the analysis as evidence, linked to it and on the timeline; the hash of an analysed file appears among the project's indicators. An ATT&CK matrix per project shows the techniques findings name (leads), your assessments (confirmed, hypothesis, ruled out, with confidence and a note) and imported ATT&CK Navigator layers such as detection coverage as an overlay with the gaps, and exports a Navigator layer of findings and assessments. The global search (`Ctrl+K`) also finds the records of open projects and opens them in their project. Five investigation playbooks (suspicious file, incident logs, vulnerable dependency, web application, cloud account) are workflow templates: they wait while you record the result in the right tool, then correlate, verify the evidence and save a report, with progress, cancellation and history.
- **IOC correlation and analysis:** the *Analysis* tab shows where each indicator of a project appears (assets, scope, findings, linked OSINT investigations, saved indicators) with cached threat-intelligence results, ranks exposure paths from an entry point to a finding, and compares the output of two tool runs. It does not contact any network.
- **Project assistant:** optional answers about one project with Claude, through the Anthropic API. It needs an API key set up by the application owner. Nothing is sent before the first question; you can preview exactly what is sent, credentials are redacted, and a system dialog asks before anything leaves your computer. Conversations are kept in memory only.
- **Security utilities:** encoders, hash, JWT, IOC and secrets tools, formatters and calculators that work offline, DNS lookups and an HTTP header analyzer, a scope-checked HTTP request builder that also works as a repeater (raw requests from a proxy, resend from the session history, side-by-side response comparison, copy as cURL), a TLS analyzer, and a review of OAuth 2.0 and OpenID Connect authorization servers: their published metadata, pasted or fetched within the project's scope, is checked against RFC 9700 for the password grant, implicit flows, missing or plain PKCE, unsigned tokens, plain-HTTP endpoints and an issuer that does not match, with the endpoints worth testing.
- **OWASP WSTG checklist:** coverage tracking.
- **Evidence vault:** files identified by SHA-256, with verification and checked exports.
- **OSINT workspace** with link analysis.
- **Reports:** HTML and Markdown reports with the same sections.
- **MCP integration:** 55 tools for Claude Code and other clients, including record search, related records, relationships and the ATT&CK matrix of a project. Sensitive actions wait for your approval in Cyber Hub; relationships a client proposes stay suggestions until you accept them.
- **Backup and restore** inside the app.

## Upgrading from earlier builds

Cyber Hub upgrades its database (`cyberhub.db`) at the first start to schema 23. **Before upgrading, it writes a complete backup** to `backups/` in its data folder and keeps the three newest. A database written by a newer version is refused, never changed. The details are in `docs/UPGRADE.md` in the source code.

### Path-level and host-level authorization

A **URL scope entry** (for example `https://app.example.com/api/`) authorizes only requests to that path, with the same scheme and port. It never authorizes the host itself:

- Port scans, service scans, TLS analysis and host names in tool arguments need the host, its domain or its address range in the scope (**host-level authorization**). The refusal says what is missing.
- Requests from the HTTP request builder are checked on the exact URL. Redirects are followed only when you ask, and every hop is checked against the scope before it is sent. Credentials (`Authorization`, `Cookie`, `Proxy-Authorization`) are not sent to another origin.
- An excluded URL excludes its path on every scheme and port. It also keeps host-level operations away from its host.

**Schema 19.** In earlier builds an excluded URL excluded its whole host. So that nothing that was excluded becomes allowed, the upgrade excludes the host of every excluded URL entry: an in-scope entry with that exact host becomes an exclusion, or a host exclusion is added. Each change is noted in the project's scope history (source "upgrade"). If you only meant to exclude the path, remove the host exclusion after the upgrade.

### Redirects of external tools

Cyber Hub cannot see where an external tool's redirects lead. A run is therefore **refused when the tool would follow redirects** and one of its URLs is authorized only by path, or lies on a host with an excluded path. The refusal names the option and says how to run the tool without redirects; Cyber Hub never changes your options. To allow redirects, authorize the host explicitly.

This applies to ffuf, gobuster, feroxbuster, httpx, dalfox, nikto, nuclei, katana, sqlmap, whatweb, wpscan and CeWL. Some of them follow redirects unless told not to: nuclei and katana need `-dr`, sqlmap `--ignore-redirects`, whatweb `--follow-redirect=never`. wpscan and CeWL always follow redirects, so they need host-level authorization. Browser modes count as following redirects (nuclei `-headless`, katana `-hl`, httpx `-ss`).

Cyber Hub does not read a tool's files of options. On these runs, an option that loads one (such as `-config`, nuclei `-tp`, sqlmap `-c` or feroxbuster `--resume-from`) is refused, and the files a tool reads on its own (such as ffuf's `ffufrc` or nuclei's `config.yaml`) are named in a warning. Their settings are not checked.

### Reports

The HTML and the Markdown report now have the same sections and terms:

- engagement details;
- executive summary;
- scope and rules of engagement;
- findings, with severity, CVSS vector and evidence (including the SHA-256 of linked files);
- vulnerabilities, assets and the evidence register.

Both list **open findings only** and count closed findings (resolved, accepted risk, false positive) instead of listing them. **Internal project notes and contacts are never included**; earlier builds exported the notes in the Markdown report. Markdown text from imports cannot turn into HTML in a viewer.

### Other changes you may notice

- **Projects:** a project cannot be deleted while one of its tool runs, workflow runs or discovery operations is still running. Tool runs and the activity log are kept, unlinked, when a project is deleted.
- **Run history:** clearing it keeps the runs that evidence, findings, OSINT evidence or discovery snapshots refer to.
- **Checklist:** links to findings can be removed, and every checklist change is recorded on the project timeline.
- **Timeline:** HTTP requests and TLS analyses sent to targets now appear there.
- **MCP:** MCP clients cannot change archived projects, and an approval of a new finding warns about a likely duplicate.

### Backup and restore

*Settings → Local data*:
- **Back up the database** saves an integrity-checked copy.
- **Restore a backup** checks the chosen file (integrity, schema version, exact schema), then restarts Cyber Hub with it. The current database is kept in `backups/before-restore-<time>/`, with the evidence files only it refers to, so you can undo a restore the same way. A backup from an earlier version is upgraded when it is opened, after its own pre-upgrade backup.

Credentials stay in the operating system's credential store and are not part of a backup. Evidence files are not part of the database backup either: keep them in an `evidence/` folder next to the backup file, and a restore copies the missing ones whose content matches their SHA-256.

## Security

- **Scope enforcement:** path-level scopes, redirect rechecks and the redirect rule for external tools are described above.
- **SQLite:** the bundled SQLite is 3.54.1. This fixes RUSTSEC-2026-0459 (CVE-2026-119375), where a crafted `-wal` file could expose uninitialized memory, a risk for restoring backups from elsewhere.
- **Audits:** `npm audit` reports no vulnerabilities. `cargo audit` reports no vulnerabilities and eight warnings about indirect dependencies of Tauri's Linux libraries: seven unmaintained crates (`proc-macro-error`, `zbus_names`, `zvariant`, `zvariant_derive`) and an unsound iterator in `glib` 0.18, which Cyber Hub's own code does not use.

## Requirements

- Windows 10 or 11 x64 with WebView2 (tested on Windows 11), or Linux x64 with WebKitGTK 4.1 (tested on Ubuntu 24.04 and Debian 12). macOS is not supported.
- Building from source: Node.js 20.19+ or 22.12+ (required by Vite 8) and **Rust 1.90 or later**.

## Known limitations

- Linux was verified on Ubuntu 24.04 and Debian 12 with a virtual display; a physical GNOME or KDE desktop and Wayland were not tested.
- Cyber Hub reads the redirect options on a tool's command line, not the settings in a tool's files of options. Options that load such a file are refused where redirects need host-level authorization, and the files a tool reads on its own are named in a warning.
- Refused tool runs are reported when they are refused but not kept in the scope history.
- If Cyber Hub is forced to quit while it copies a backup for a restore, the unfinished copy (a hidden `.restore-….partial` file) stays in the data folder. It is never used and can be deleted.
- The project assistant was tested against a local stand-in for the Anthropic API, not the live service.
- The full list is in `docs/SECURITY.md` (*Accepted risks and limitations*) in the source code.
