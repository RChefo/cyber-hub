# Cyber Hub 0.1.0

Cyber Hub is a local-first workstation for authorized security assessments. Projects keep their authorized scope, findings, evidence, tool runs and reports together, and every tool that sends traffic is checked against that scope before it runs. Your data stays on your computer.

## Highlights

- **Projects with an authorized scope:** domains, wildcards, addresses, networks, ranges and URL entries, with exclusions. Runs, imports, discovery and MCP requests are checked against it, and refused attempts are kept in the scope history.
- **Findings:** a lifecycle with history, CVSS 4.0 and 3.1 vectors scored as in FIRST's calculators, a finding library with templates, and bulk editing.
- **Imports:** Nmap, Nuclei, Nessus, Greenbone/OpenVAS, Burp Suite, OWASP ZAP and SARIF results, and CSV files with a column mapping. Imports deduplicate, check the scope and verify fixes by rescan. CVEs can optionally be tracked as vulnerabilities.
- **Vulnerability management:** EPSS, CISA KEV and transparent priorities.
- **OWASP WSTG checklist:** coverage tracking.
- **Evidence vault:** files identified by SHA-256, with verification and checked exports.
- **Assessment workspace:** an OSINT workspace with link analysis, attack-surface discovery, workflows and a project timeline.
- **Reports:** HTML and Markdown reports with the same sections.
- **MCP integration:** 49 tools for Claude Code and other clients. Sensitive actions wait for your approval in Cyber Hub.
- **Backup and restore** inside the app.

## Upgrading from earlier builds

Cyber Hub upgrades its database (`cyberhub.db`) at the first start to schema 19. **Before upgrading, it writes a complete backup** to `backups/` in its data folder and keeps the three newest. A database written by a newer version is refused, never changed. See [docs/UPGRADE.md](../UPGRADE.md).

### Path-level and host-level authorization

A **URL scope entry** (for example `https://app.example.com/api/`) authorizes only requests to that path, with the same scheme and port. It never authorizes the host itself:

- Port scans, service scans, TLS analysis and host names in tool arguments need the host, its domain or its address range in the scope (**host-level authorization**). The refusal says what is missing.
- Requests from the HTTP request builder are checked on the exact URL. Redirects are followed only when you ask, and every hop is checked against the scope before it is sent.
- An excluded URL excludes its path on every scheme and port. It also keeps host-level operations away from its host.

**Schema 19.** In earlier builds an excluded URL excluded its whole host. So that nothing that was excluded becomes allowed, the upgrade excludes the host of every excluded URL entry: an in-scope entry with that exact host becomes an exclusion, or a host exclusion is added. Each change is noted in the project's scope history (source "upgrade"). If you only meant to exclude the path, remove the host exclusion after the upgrade.

### Redirects of external tools

Cyber Hub cannot see where an external tool's redirects lead. A run is therefore **refused when the tool would follow redirects** and one of its URLs is authorized only by path, or lies on a host with an excluded path. The refusal names the option and says how to run the tool without redirects; Cyber Hub never changes your options. To allow redirects, authorize the host explicitly.

This applies to ffuf, gobuster, feroxbuster, httpx, dalfox, nikto, nuclei, katana, sqlmap, whatweb, wpscan and CeWL. Some of them follow redirects unless told not to: nuclei and katana need `-dr`, sqlmap `--ignore-redirects`, whatweb `--follow-redirect=never`. wpscan and CeWL always follow redirects, so they need host-level authorization.

### Reports

The HTML and the Markdown report now have the same sections and terms:

- engagement details;
- executive summary;
- scope and rules of engagement;
- findings, with severity, CVSS vector and evidence (including the SHA-256 of linked files);
- vulnerabilities, assets and the evidence register.

Both list **open findings only** and count closed findings (resolved, accepted risk, false positive) instead of listing them. **Internal project notes and contacts are never included**; earlier builds exported the notes in the Markdown report. Markdown text from imports cannot turn into HTML in a viewer.

### Other changes you may notice

- **Projects:** a project cannot be deleted while one of its tool runs, workflow runs or discovery operations is still running. Tool runs and the activity log are kept, unlinked, when a project is deleted.
- **Run history:** clearing it keeps the runs that evidence, findings, OSINT evidence or discovery snapshots refer to.
- **Checklist:** links to findings can be removed, and every checklist change is recorded on the project timeline.
- **Timeline:** HTTP requests and TLS analyses sent to targets now appear there.
- **MCP:** MCP clients cannot change archived projects, and an approval of a new finding warns about a likely duplicate.

### Backup and restore

*Settings → Local data*:
- **Back up the database** saves an integrity-checked copy.
- **Restore a backup** checks the chosen file (integrity, schema version, exact schema), then restarts Cyber Hub with it. The current database is kept in `backups/before-restore-<time>/`, with the evidence files only it refers to, so you can undo a restore the same way.

Credentials stay in the operating system's credential store and are not part of a backup. Evidence files are not part of the database backup either.

## Security

- **Scope enforcement:** path-level scopes, redirect rechecks and the redirect rule for external tools are described above.
- **SQLite:** the bundled SQLite is 3.54.1. This fixes RUSTSEC-2026-0459 (CVE-2026-119375), where a crafted `-wal` file could expose uninitialized memory, a risk for restoring backups from elsewhere.
- **Audits:** `cargo audit` and `npm audit` report no vulnerabilities.

## Requirements

- Windows 10/11 x64 (WebView2), or Linux x64 (WebKitGTK 4.1). macOS is not supported.
- Building from source: Node.js 20 or later and **Rust 1.90 or later**.

## Known limitations

- Linux was verified on Ubuntu 24.04 and Debian 12 with a virtual display; a physical GNOME or KDE desktop and Wayland were not tested.
- Cyber Hub reads the redirect options on a tool's command line, not settings inside a tool's own configuration file.
- See [docs/SECURITY.md](../SECURITY.md#accepted-risks-and-limitations) for the full list.
