# Security utilities

Security Utilities (sidebar) groups local tools (encoders, parsers, formatters) and network tools. This page describes the tools added with the platform expansion. The backend code is in `src-tauri/src/sectools/` and `src-tauri/src/commands/sectools.rs`; the views are in `src/modules/utilities/tools/AssessmentTools.tsx`.

| Tool | Contacts | Rules |
|---|---|---|
| HTTP request builder | the URL's host | **Project required; active scope gate** on the URL host and on any `Host` header (another virtual host is another target). The project must be active. Methods GET, HEAD, POST, PUT, PATCH, DELETE, OPTIONS; at most 50 headers (no line breaks, `Content-Length`/`Transfer-Encoding` set automatically); body ≤ 1 MB; response read ≤ 2 MB; 20 s time limit; redirects followed only when asked, at most 5, each checked against the scope before it is sent; untrusted certificates only with an explicit switch. A host name is resolved once and refused if it points at a private, loopback, link-local or reserved address that is not itself in the scope; the request then connects only to the checked addresses (DNS-rebinding protection). A response that is not HTTP is reported as such. **Repeater:** a raw request pasted from a proxy or the browser (with an optional target, otherwise the `Host` header over HTTPS), resend from the session history, comparison of two responses (status, timing, size, changed headers, line diff of the bodies) and *Copy as cURL*; a request opened from a project's API inventory arrives prefilled. Every send goes through the same checks. The history stays in memory until Cyber Hub closes and is never saved, because requests can carry credentials; the activity log records method, URL (credentials redacted) and status. |
| TLS analyzer | the host and port | **Project required; active scope gate**, with the same resolved-address check as the HTTP request builder. Up to three handshakes (TLS 1.2+1.3, 1.3 only, 1.2 only), nothing sent after them. Reports the negotiated protocol and cipher, ALPN, the certificate chain (subject, issuer, validity, names, key, signature, SHA-256), and trust against the system roots. Issues are graded critical, warning or note. TLS 1.0/1.1 cannot be tested (rustls does not implement them) and the report says so. The certificate is recorded as a project asset (`certificate`, keyed by fingerprint). |
| OAuth & OpenID Connect review | the issuer's metadata addresses, only when fetching | Reviews the authorization server metadata of an OpenID Connect provider (`/.well-known/openid-configuration`) or an OAuth 2.0 server (RFC 8414, `/.well-known/oauth-authorization-server`), pasted, opened from a file or fetched (`utilities/lib/oauth.ts`). **Fetching** needs a project and goes through the HTTP request builder's command: **active scope gate** and the same resolved-address check, one GET to the OpenID Connect address and, if it is missing, one to the RFC 8414 address; redirects are followed only within the scope, and no authorization or token request is ever made. **Issues**: endpoints over plain HTTP (high; loopback addresses excepted), an issuer that differs from the address the document was fetched from (high, OpenID Connect Discovery 4.3 and RFC 8414 3.3), the resource owner password grant (high, RFC 9700 2.4), "none" among the signing algorithms of ID tokens or client authentication JWTs (high) or of request objects, UserInfo or authorization responses (medium, RFC 8725 3.2), access tokens in the authorization response (implicit or hybrid, medium, RFC 9700 2.1.2), PKCE with the plain method only (medium, RFC 9700 2.1.1), HMAC-signed ID tokens (low, RFC 8725 3.5) and RSA1_5 encryption (low). **To test** (leads, never recorded as findings): PKCE that is not advertised, request objects fetched from client-supplied `request_uri` addresses (supported by default), dynamic client registration (both server-side request forgery paths described by PortSwigger Research) and the device authorization grant (RFC 8628 5.4). Strengths are listed too (PKCE with S256, pushed authorization requests, DPoP, mTLS-bound tokens, `iss` in authorization responses, asymmetric client authentication), with the endpoints, which open in the HTTP request builder, and what the server advertises, with the specifications' defaults for absent fields. Issues can be recorded as findings (category *OAuth configuration*), once each; when the metadata was fetched, the project it was fetched for is preselected. The metadata shows what the server offers, not how each client is configured. |
| DNS intelligence | the system resolver | **Passive scope gate:** internal and single-label names are refused, and project exclusions apply when a project is chosen. The tool queries A, AAAA, CNAME, NS, MX, SOA, TXT, CAA, `_dmarc`, ten common DKIM selectors and DNSKEY. It assesses SPF (`+all`, missing or weak `all`, duplicate records, more than 10 lookups), DMARC (missing, `p=none`, partial `pct`, no reports), DKIM, CAA and DNSSEC. Domains without MX get advice, not warnings. |
| Port & service reference | nothing | Offline reference of common ports: service, typical risks, checks. It also lists where recorded project services expose the port. |
| Subdomain monitor | public sources only | Shows new and missing names across a project's passive discovery runs, with certainty. *Monitor on a schedule* creates or updates a passive-only workflow ([WORKFLOWS.md](WORKFLOWS.md)). |
| IOC extractor (Analysis) | nothing | Extracts URLs, domains, IPv4 and IPv6 addresses, e-mail addresses, MD5/SHA-1/SHA-256/SHA-512 hashes and CVE IDs from pasted text (≤ 2 MB, ≤ 5,000 per kind). It first refangs `hxxp`, `[.]`, `(.)`, `{.}`, `[dot]`, `[:]`, `[://]`, `[@]` and `[at]`. File names such as `report.pdf` or `payload.exe` are not taken for domains (common file extensions are excluded as top-level domains, except those that are real top-level domains: com, zip, mov, pl, sh, md, rs, py). Patterns are bounded so long pasted inputs stay fast (tested on hostile 40,000-character runs). IPv6 candidates are validated, so times and MAC addresses are not reported. Output is defanged (CyberChef style) or plain; IPs, domains, URLs and hashes open in Threat Intel for a lookup. The transform workbench has *Defang indicators* and *Refang indicators* operations. Code: `src/modules/utilities/lib/ioc.ts`. |

A folder is searched to 50,000 entries and 2,000 configuration files of at most 5 MB, without following links and without .git, node_modules, vendor, target and build folders; Helm templates are reported as needing `helm template` first. | File triage (PE, ELF) | nothing | Reads one file chosen in a native dialog (up to 256 MB, `sectools/binary.rs`); the file is never run or uploaded. ### Hunting leads in packet captures

Packet capture triage reports hunting leads (`sectools/pcap_hunt.rs`) apart from its issues, and each lead says what else it can be. Up to 100 leads of each kind are listed.

* **Regular schedules:** connections from a client to a server on a regular schedule (beacon-like timing). TCP connections count by their SYN, and UDP packets more than a second apart count as separate exchanges. At least six connections over two minutes or more are needed. The interval is the mean of the gaps within a quarter of the median gap, so missed connections and alternating jitter do not distort it. *Regular* means the gaps stay within 10% of the interval with 80% on schedule; *jittered* means within 25% with 60%. DNS, NTP, DHCP, NetBIOS, SNMP, syslog, SSDP, WS-Discovery, mDNS and LLMNR are marked as scheduled by design.
* **DNS patterns:** many long or high-entropy names under one domain (tunneling or exfiltration; also CDNs, anti-virus lookups and telemetry), very long labels, 20 or more TXT, NULL or ANY queries to one domain, and 25 or more NXDOMAIN answers to one client across 15 or more domains (generated domains; also typos and prefetching). Domains are grouped by their last two labels, or three under a two-letter country code with a common second level. Reverse lookups and local names are left out.
* **As findings:** the leads the analyst records become findings under review with low confidence, in the category *Threat hunting*. They carry no ATT&CK tag, since a pattern shows no technique; the technique that would apply if a lead were confirmed is named in the text.

**Recording results in a project.** File triage, packet capture triage, log and Windows event log triage and the OAuth review record the selected issues as findings through one backend command (`commands/utility_record.rs`), in one transaction. With *Keep the file as evidence* (on by default) the file that was analysed is copied into the project's evidence vault; the web view never names it: the analysis returns a random token for the file, the file is read again when it is stored and refused if its SHA-256 is no longer the one analysed. The analysis itself is kept as text evidence (JSON, derived from the file), each finding is linked to the file (or, without a file, to the analysis), and the timeline and the activity log record the step. Both evidence records carry their provenance (module, tool, Cyber Hub's version). Findings are recorded once per title; recording again links the existing findings and keeps the same analysis once. Archived projects are not offered. See [DATA_MODEL.md](DATA_MODEL.md#utility-results).

The existing DNS lookup and HTTP header analyzer are unchanged. The wordlist manager (Wordlists page) covers the wordlist part of the expansion request: indexing by reference or managed copy, folder scans, preview, export and safe delete.

The scanner commands are named `leak_scan_*`: an existing test refuses any IPC command whose name contains "secret", so that no command can read or change stored credentials.
