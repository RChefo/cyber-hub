# Security model

Cyber Hub launches security software. Its security goals:

1. Nothing runs without an explicit human decision made outside the web page.
2. Tools that touch the network only reach targets inside an active project's authorized scope.
3. Data stays on the device; credentials are never persisted in clear text.
4. A compromised or buggy frontend cannot turn the app into a general-purpose command runner or file reader.

## Trust boundaries

```
web view (React)  ──IPC──▶  Rust commands  ──▶  process manager / file system / SQLite / OS credential store
   untrusted for            validate every                 native OS dialogs gate every
   consequential actions    input & path                   process start
```

The web view is treated as **untrusted for consequential actions**. Everything that starts a process, chooses a file path or writes outside the app's own database is decided in Rust and, where it starts a process, confirmed in a native OS dialog the page cannot script.

## Controls

| Area | Control |
|---|---|
| Process start | `exec_start` and `tool_install` show a **native OS confirmation dialog** (Win32 task dialog / AppKit / GTK, created by the Rust process) with the exact program, arguments (credentials redacted), project and authorized targets. Page script cannot see or click it. Cancelling returns a `cancelled` error and starts nothing. |
| No shell | Processes are spawned with argv through `tokio::process::Command`, never `sh -c` / `cmd /c`. stdin is closed. |
| Executables | Resolved by the backend from the catalog (or the allow-listed package managers `winget`, `brew`, `pipx`, `go`). Only **absolute PATH entries** are searched (relative entries such as `.` are ignored to prevent binary planting). On Windows only native `.exe`/`.com` files are executed with arguments — `.bat`/`.cmd` wrappers are refused because `cmd.exe` re-parses their arguments. Helper programs use fixed absolute paths (`/usr/bin/open`, `%SystemRoot%\System32\WindowsPowerShell\v1.0\powershell.exe`). |
| Arguments | ≤ 256 arguments, ≤ 4096 chars each, no NUL / CR / LF. Execution requests with unknown fields (e.g. a working directory) are rejected. |
| Scope | Scope-required tools need an **active** project with in-scope entries; every target named anywhere in the arguments — including inside target files — must be in scope (see below). New operations decide through one scope gate (`workspace/scope_gate.rs`): active operations need an active project and in-scope targets, passive lookups never send private, reserved or internal targets to public sources and respect exclusions. Blocked active attempts and every scope change are recorded in the project's scope history. |
| Process trees | Windows: each run is assigned to a Job Object with `KILL_ON_JOB_CLOSE`; cancel terminates the job; leftover descendants die when the run ends or Cyber Hub exits. Unix: each run gets its own process group; cancel sends SIGTERM then SIGKILL to the group; Cyber Hub kills all running groups on exit. |
| Output | Lines are read in bounded chunks (16 KB); stored output is capped at 2 MB per run. |
| Redaction | Before anything is persisted (run arguments, stored output, command history, activity details) credentials are redacted: options named like passwords/tokens/secrets/cookies/API keys, URL user-info, `Authorization`/`Cookie`/API-key headers, secret-named `key=value` pairs, `domain/user:password@host`, and JWTs. Redaction is lossy by design. |
| Temporary files | Validated target files are snapshotted into `<app data>/runtime/run-*`, read by the tool from there, and deleted when the run ends; the whole `runtime` directory is cleared at startup and exit. |
| Attack surface discovery | Passive runs only ask public sources (crt.sh, DNS) about in-scope public domains; discovered names outside the scope are not recorded. Web checks and service scans contact targets only after the active scope gate and a native confirmation; service scans use fixed Nmap profiles (`-sV -T3 [-F] -oX -`, no scripts, nothing written to disk) through the normal execution path, which checks every argument again. Missing results never delete assets; only completed runs mark them as not observed. |
| Assistant | Owner-provisioned Anthropic key (`cyberhub-keys`), read only by the backend. The selected project data (credentials redacted, ≤ 150,000 characters) is sent only after a native confirmation naming the destination and size; the model has no tools; project data is wrapped as untrusted data and the system prompt forbids following instructions inside it; answers are shown as plain text; conversations stay in memory. See [ASSISTANT.md](ASSISTANT.md). |
| Security utilities | The HTTP request builder and the TLS analyzer need a project and pass the active scope gate (the HTTP builder also checks a `Host` header); DNS intelligence passes the passive gate; the secrets scanner reads only files chosen in a native dialog, never follows symbolic links and returns masked matches. See [UTILITIES.md](UTILITIES.md). |
| Reports | HTML reports are rendered by the backend with every value escaped and a report-level Content-Security-Policy that forbids scripts and remote content; the preview frame is sandboxed without scripts, and the print frame allows only same-origin access (so the app can start printing) and modals, not scripts. Saving uses a native dialog. |
| Workflows | Only predefined step types with validated settings ([WORKFLOWS.md](WORKFLOWS.md)); no scripts, commands or URLs. Runs with steps that contact targets need a native confirmation listing them and their scope-checked targets; every step is checked against the scope again when it runs; service scans still show the execution engine's confirmation. Only workflows without such steps can be scheduled, and that is checked again before every scheduled run. |
| Scan import | Files are chosen in a native dialog opened by the backend (the web view never supplies a path) and limited to 50 MB, 10,000 findings and 20,000 asset values. The format is recognized from the content. XML is read with a streaming parser that skips a DOCTYPE and never expands entities or reads external resources (XXE); unknown entities stay as written. Every network target passes the scope engine; out-of-scope results are not recorded. Request and response bodies are not copied; copied text is redacted. Nothing is contacted. See [DATA_MODEL.md](DATA_MODEL.md#scan-import-schema-13). |
| Evidence files | Added and exported only through native dialogs opened by the backend. Files are copied into `<app data>/evidence` under their SHA-256 (the original name is a label and never part of a path), limited to 256 MB while reading, deduplicated per project, and removed with the last record that refers to them; symbolic-link folders are refused, Unix folders are `0700`. References to runs and OSINT evidence are accepted only from the same project. |
| File system | The web view never supplies file paths. Wordlist import, the extra wordlist folder and wordlist export use native dialogs opened by the backend. Preview reads only indexed files (≤ 64 MB). Deleting a wordlist file is limited to the managed folder (canonical-path check). |
| Tauri capabilities | The main window gets only: `opener:allow-open-url` restricted to `http(s)://*`; for the frameless window and its controls `core:window:allow-start-dragging`, `allow-minimize`, `allow-toggle-maximize`, `allow-internal-toggle-maximize`, `allow-is-maximized` and `allow-close`; and `core:event:allow-listen` / `allow-unlisten` so the maximize/restore button can follow resize events. No `core:default`, no shell, no fs, no dialog, no HTTP permissions. |
| `freezePrototype` | **Enabled.** `Object.prototype` is frozen in the web view. Chart dependencies that relied on the JavaScript "override mistake" are patched at install time (`scripts/patch-deps.mjs`, exact-statement rewrites to `Object.defineProperty`, verified by a self-test that loads them with a frozen prototype; the install fails if any patch no longer applies). |
| CSP | `default-src 'self'`; scripts from self only; no remote origins for connect/img/font; `frame-ancestors 'none'`; `form-action 'none'`. `style-src` allows inline styles (required by HeroUI / motion). |
| Secrets | All service credentials (VirusTotal, AbuseIPDB, OTX, abuse.ch, Shodan, NVD) are provisioned by the application owner with the developer-only `cyberhub-keys` tool ([PROVISIONING.md](PROVISIONING.md)) and kept in the OS credential store (Windows Credential Manager, Linux Secret Service). The app only reads them. **No IPC command can read, list, set, test or delete a credential**; the web view only learns whether a provider is configured. A unit test fails if such a command is registered again. |
| Updates | Official Tauri updater plugin, driven only by the backend (the web view has no updater permission). Every package is verified against the public key compiled into the app (minisign) and must be signed for the version the feed announces (`requireSignedVersion`); feeds and downloads must use HTTPS (an invalid certificate is never accepted); only newer stable versions are offered (no downgrades); downloads stay in memory until installed; installing needs a click and a native confirmation and is refused while runs, collections, MCP approvals or uploads are in progress. The private signing key exists only in the owner's key file and the release environment's secrets. Details: [UPDATER.md](UPDATER.md). |
| Network | No telemetry. The optional automatic update check (on by default, Settings → Updates) fetches only the release manifest from the feed compiled into release builds; it sends no data beyond a standard request. All other requests happen only on explicit actions: live CVE search (services.nvd.nist.gov; also when a vulnerability is tracked whose CVE is not cached), EPSS scores from api.first.org when a vulnerability is tracked or scores are updated (only CVE IDs are sent; can be turned off), assistant questions to api.anthropic.com (after a native confirmation; see the Assistant row), threat-intelligence lookups and VirusTotal file uploads (see below), DNS lookup (system resolver), HTTP header fetch (the URL entered; redirects not followed; body not read), opening links. |
| Preferences | Settable keys are allow-listed and some are range-checked (the VirusTotal upload limit must be 1–650 MB); the wordlist folder can only be set through the native folder picker. |

## Threat-intelligence providers

Providers, endpoints and documented access conditions are listed in [PROVIDERS.md](PROVIDERS.md).

| Concern | Control |
|---|---|
| Credentials | Provisioned by the application owner (see [PROVISIONING.md](PROVISIONING.md)); one OS credential-store entry each. A credential is read only inside the Rust function that sends the request, and is sent only to that provider's fixed API base. It goes in a header (`x-apikey`, `Key`, `X-OTX-API-KEY`, `Auth-Key`, NVD `apiKey`), or for Shodan in the `key` query parameter its API requires. Credentials never cross IPC and are never written to SQLite, history, exports or logs. |
| Error messages | Transport errors are reported without their URL (`without_url`), and every provider message is scrubbed of the key before it reaches the UI. This covers Shodan's query-string key. `x-apikey` and API-key headers are also covered by the output redaction rules. |
| Provisioning and diagnostics | Only through `cyberhub-keys`, which is compiled only with the `provisioning` Cargo feature and not included in application builds or installers. It takes values from a hidden prompt, standard input or a git-ignored local file, never from arguments. Before storing, it verifies each credential with one fixed public probe (VirusTotal and AbuseIPDB `8.8.8.8`; OTX subscribed pulses; abuse.ch the EICAR test hash; Shodan `/api-info`; NVD a fixed CVE). It also provides `status` / `test` (sanitized, values never printed) and `remove`. In the app, Settings shows read-only availability only: Not configured, Turned off, Available, Rate limited, Credentials rejected or Last request failed, plus reported quota, all observed from real lookups. |
| Fixed endpoints | Production API bases are constants (`ti::ProviderId::production_base`). Requests never follow redirects, and response bodies are read incrementally and capped at 8 MB (including chunked responses). A debug-only override (`CYBERHUB_MOCK_API_BASE`, parsed and accepted only as `http://127.0.0.1:<port>` or `http://localhost:<port>` with no credentials, path or query) routes every provider to a local mock for testing; it is compiled out of release builds (`cfg(debug_assertions)`). |
| No arbitrary requests | The web view sends only the indicator text and the provider IDs to use. The backend validates the indicator, builds every path and body itself and uses its own stored keys. No command accepts a key, URL or header for a lookup, and the web view has no HTTP permission. |
| Private data | Private, loopback, link-local, CGNAT, documentation and other reserved IP addresses are refused before any provider is contacted. IPv6 forms that embed an IPv4 address (mapped, IPv4-compatible, NAT64 `64:ff9b::/96`, 6to4 `2002::/16`) are judged by the embedded address, and `fec0::/10` and `192.0.0.0/24` are refused. URLs on such addresses, single-label names and internal suffixes (`.local`, `.internal`, `.corp`, `.lan`, `.home.arpa`, …) are refused too. Only http(s) URLs without embedded user names or passwords are accepted. |
| Isolation | Providers run concurrently and independently. A missing key, a disabled provider, a rate limit, an HTTP error or an unparsable response becomes a status on that provider's result and never fails the others. |
| Rate limits and cache | Each provider has its own client-side limit at or below its documented allowance (VirusTotal 4/min, Shodan 1/s, AbuseIPDB and OTX 30/min, abuse.ch 20/min). Provider quota errors are shown as such. Results are cached per provider (`vt_cache`, `ti_cache`; 6–24 h for records, 1 h for "no record"); errors are not cached. Refresh bypasses the cache explicitly. |
| Verdicts | Each provider's verdict is kept in its own wording, and scores are never combined. The colour buckets per provider are documented in [PROVIDERS.md](PROVIDERS.md). |
| No external actions | Nothing is reported, submitted, blocked or changed at a provider. Pivoting to a related indicator only starts another read-only lookup after the user selects it. |
| History and exports | Each multi-provider search is recorded in `ti_history` (indicator plus the list of providers per outcome) and in the activity log. Reports are exported from stored results only (no network) through a native save dialog. Provider-written text in Markdown exports is escaped, so it cannot form links, images, headings or HTML, and control and line-separator characters are removed. Links come only from Cyber Hub's own URL patterns or, for URLhaus, must point to `https://urlhaus.abuse.ch/`. |

## OSINT workspace

- Public-source collection runs only in the backend. Private, loopback, link-local and reserved addresses and internal names are refused before anything is sent (`osint::discovery::check_public`).
- The only source that contacts a target directly (web fingerprint) requires a linked, active project whose authorized scope covers the target, uses the same scope engine as tool runs, resolves the name itself, checks every address and pins the checked public addresses for the connection, so DNS rebinding cannot redirect it to an internal host. It sends HEAD (GET only when HEAD is refused), follows no redirects and never reads the body.
- RDAP servers come only from the IANA bootstrap files; they must be `https://` URLs on public hosts, and redirects are not followed. Other sources use fixed endpoints.
- All requests of public sources resolve host names through a resolver that returns only public addresses (`osint::providers::PublicOnlyResolver`); if a name resolves only to private, loopback, link-local, carrier-grade NAT, documentation or other reserved addresses (including IPv4-mapped IPv6), the request fails before any connection. This closes DNS rebinding and hostile records for source hosts as well as for targets.
- Graph saves use optimistic concurrency: a save based on an older saved state is refused (`conflict`) unless the analyst chooses to overwrite; the overwritten state remains in the version history.
- Responses are size-limited, per-source rate limits apply, and at most six collections run at once. Downloaded content is never executed and collected pages are not rendered.
- Threat-intelligence and NVD access reuse the existing modules; keys stay in the OS credential store and never appear in investigations, evidence, exports, logs or MCP responses. Tests use fixtures and never call real services.
- Collected text is untrusted. It is shown as plain text (references are selectable, not clickable), escaped in SVG, GraphML and Markdown output, and CSV cells that start with `=`, `+`, `-`, `@`, tab or carriage return are prefixed with `'`. MCP clients are told to treat it as data and not follow instructions in it.
- Nothing is verified automatically. Inferred correlations need review, analyst decisions are never overwritten by collection, imported files cannot carry verification, and MCP clients can only propose relationships (stored as unverified suggestions) and start collections whose results wait for review.
- Imports are limited to 25 MB and fixed element counts, must be UTF-8, refuse GraphML with a DOCTYPE (no entity expansion), detect duplicate IDs, are previewed, and always create a new graph.
- Deleting an investigation or a graph needs a native confirmation.
- On Linux the application data folder (database, investigations, evidence) is set to `0700` at every start, regardless of the umask; on Windows the profile folder is already private to the user.

## MCP integration

Details: [MCP.md](MCP.md).

| Concern | Control |
|---|---|
| Exposure | Off by default. When enabled, the app listens only on `127.0.0.1` (random port; non-loopback peers are dropped), with at most 16 open sockets (authenticated or not), 8 authenticated connections and 8 in-flight requests per connection. Turning it off or exiting closes every connection, aborts in-flight requests, cancels pending approvals and deletes the connection files. |
| Authentication | `cyberhub-mcp` and the app authenticate each other with HMAC-SHA256 over fresh nonces, using a 256-bit key that is regenerated for every session and stored in the user's app-data directory (mode 0600 on Unix). A process without the key cannot use the bridge or impersonate the app. Any process running as the same OS user can read the key; that user is the trust boundary. After the handshake, frames are not individually authenticated: the loopback TCP connection is trusted for its lifetime, as with any local socket. |
| No second execution path | Runs requested through MCP use `start_execution` (scope engine with exclusions, target-file snapshots, native confirmation, process trees). Previews use the same validation. MCP cannot name a program outside the catalog, use a shell or pass unknown fields. The approval and the native confirmation show the arguments unredacted, exactly as they will run, and say so when a tool is not scope-checked. |
| Sidecar | `cyberhub-mcp` is installed next to the app as a Tauri sidecar and is located from the app's own executable path, never from the working directory or PATH. It is built without the `provisioning` feature and contains no credentials (checked in the release binary). The app does not start it; MCP clients do. |
| Approvals | The policy for each category is set only in Cyber Hub's window. Sensitive requests are validated first (invalid or out-of-scope requests never reach the user), then shown in Cyber Hub for the user's decision. Runs, uploads and exports still go through their native dialogs. The decision, policy and enable commands are Tauri commands for the app's own window and are not reachable through the bridge (a unit test checks the catalogue). Requests expire after 3 minutes (an overdue request can no longer be approved), are cancelled when the client disconnects, and are capped at 20 in total and 5 per connection. Requests are decided in the Approval Center on the MCP page (or in a dialog elsewhere in the app); both call the same `mcp_decide` command. The Approve button is disabled for one second whenever the waiting requests change, so a click aimed at one request cannot approve another, and an expired request cannot be approved. `cyberhub_cancel_run` only stops runs started through MCP. |
| Files | MCP clients never supply paths. Run and preview arguments that look like local files (drive letters, `\`, `/` outside URLs and CIDR ranges, `.`, `~`, `@` prefixes, `file:` URLs, option values attached to the option letter such as `-rC:\x` or `-oN/tmp/out`, or the name of an existing file) are refused with one generic message, so a client can neither read target lists nor learn whether a file exists; file-based runs are started in Cyber Hub. Uploads use the native file picker (an optional `expected_sha256` must match), and exports use the native save dialog. Tool outputs show only the program's file name and replace absolute paths in stored arguments with `<local file>`. |
| Credentials | No MCP operation reads, returns or changes a credential. `cyberhub-mcp` holds none, and the provisioning tool is not compiled into it. |
| Input limits | MCP arguments are capped at 256 KiB and bridge frames at 4 MiB. Strict typed parsing rejects unknown fields. Handshakes time out after 5 s, and each MCP call is bounded (50 s approval wait, 120 s overall). Live output per run is capped at 5,000 lines. |
| Audit | Every call is logged, including refused and unknown ones, with the client (self-reported), tool, redacted arguments, project, approval outcome, run ID, result, redacted error message and duration. Approved requests are logged with their final outcome, also when the user decides after the client stopped waiting. The newest 1,000 ordinary entries are kept, and entries tied to an approval or a run are kept separately (newest 5,000), so a client cannot flush the record of approved actions by flooding cheap calls. |
| Protocol hygiene | `cyberhub-mcp` writes only MCP messages to stdout; diagnostics go to stderr. |

## VirusTotal file analysis

| Concern | Control |
|---|---|
| File selection | `vt_file_pick` opens the native file picker in the backend. The web view receives an opaque random handle plus the file name, size and hashes, never a path. Handles expire after one hour (at most ten are kept). Only regular files are accepted (links are resolved first); files over 2 GB are not hashed. |
| Hash first | SHA-256, SHA-1 and MD5 are computed locally. "Look up hash" sends only the SHA-256 (a normal reputation lookup). A missing report never triggers an upload. |
| Explicit confirmation | Uploading requires (1) an in-page acknowledgement that the file is shared publicly and contains no sensitive data, reset after every attempt, and (2) a **native OS dialog** for that file, showing its name, size, SHA-256 and the public-sharing warning. Page script cannot see or click that dialog. Declining returns `cancelled`, and nothing is read for upload or sent. |
| Public, not private | The upload is a standard public submission and is labelled as such everywhere. Private scanning is not implemented (see PROVIDERS.md). |
| Original file untouched | The file is copied into a private snapshot under `<app data>/runtime` while being re-hashed. If its size or SHA-256 differs from what was shown at selection, nothing is uploaded. The upload streams from the snapshot, which is deleted when the operation ends (success, error or cancellation) and also at app start and exit. The original file is never written, moved or deleted. |
| Size limits | A user-configurable limit (default 32 MB, 1–650 MB) is checked before the confirmation. Files ≤ 32 MB use `POST /files`. Larger files use `GET /files/upload_url`, and the returned one-time URL must be an HTTPS `virustotal.com` host without credentials or a custom port (the documented `http://` form is upgraded to HTTPS). Otherwise the file is not sent. Uploads count against the local 4/minute limit (two requests for the upload-URL flow). Availability is checked before the confirmation without using quota, and the slots are taken only after approval. Only one upload per selected file can run at a time. |
| Cancellation | An upload in progress can be cancelled; the request is dropped and the snapshot deleted. VirusTotal may already have received part of the file. |
| Analysis | The analysis ID is validated (base64-style characters, ≤ 256) and percent-encoded into `GET /analyses/{id}`. The UI polls every 20 seconds for up to 30 minutes; each poll counts against the quota. When the analysis completes, the file report is fetched and shown. |
| Recording | Each upload is recorded in the activity log (file name, SHA-256, size). File contents are never stored. |

Tests:
* `src-tauri/src/vtfile.rs`: hash vectors; nothing is uploaded and no snapshot is created when the confirmation is declined; an approved upload sends exactly the file as multipart with the key only in the header, then deletes the snapshot; size limit enforced before asking; a file changed after selection is refused; cancellation after approval sends nothing; large files use the upload URL; a foreign upload URL is refused; upload-URL, analysis-ID and file-name sanitising.
* `src-tauri/src/ti/*.rs`: per-provider parsing fixtures and local mock HTTP servers. They check where each key is sent, error mapping, that errors never contain the key (including Shodan's query-string key), and that unsupported hash types make no request.

## Scope enforcement

Scope entries:

| Entry | Matches |
|---|---|
| `example.com` | exactly `example.com` |
| `*.example.com` | any sub-domain at any depth (not the apex) |
| `10.0.0.5` | that address (IPv4-mapped IPv6 such as `::ffff:10.0.0.5` is normalized and matches too) |
| `10.0.0.0/24` | addresses and sub-networks fully inside it |
| `https://app.example.com` | the URL's host |
| out-of-scope entry | always wins; a network or IPv4 range that **overlaps** an excluded host or network is rejected |

### Target resolution (tool-independent)

For a scope-required run every argument value (whole positional values and the part after `=` in `--opt=value`) is examined:

* **Existing files** are read and classified:
  * *raw HTTP request* (`METHOD target HTTP/x` first line): the `Host` header and an absolute request-line URL must be in scope; duplicate `Host` headers are rejected;
  * *target list* (any line names a network endpoint): **every** non-comment line must parse strictly (hosts, IPs, `[IPv6]:port`, CIDRs, IPv4 ranges, URLs) and every entry must be in scope — wildcards like `10.0.0.*`, single-word names (which may resolve through DNS search domains) and other unparseable lines reject the run;
  * *data* (wordlists, payloads, binaries): allowed.
  Target lists and requests are **snapshotted** and the argument rewritten to the snapshot; the snapshot is re-validated after copying, so a file swapped during validation is detected.
* **Other values** are scanned for URLs (any host, including single-label hosts and decimal IPs such as `http://2130706433/` which normalizes to 127.0.0.1), IPs, `[IPv6]`, CIDRs, IPv4 ranges, `host:port` (including single-label), `user@host` / `domain/user:pass@host`, `localhost`, and dotted host names. File-name heuristics only exclude extensions that are **not** top-level domains (`.zip`, `.py`, `.sh`, `.pl`, `.md` are real TLDs and are checked as hosts).
* Explicit targets from builders are parsed strictly.
* At least one target must be identified, otherwise the run is refused.

Fuzzing keywords in host names need no special handling: `https://FUZZ.example.com/` is a real host under `*.example.com` and passes only if that wildcard is in scope, while `https://exaFUZZ.com/`, `https://FUZZ/` or `https://10.0.0.FUZZ/` name other hosts and are rejected.

Tests: `src-tauri/src/scope.rs` and `src-tauri/src/targets.rs` (target files, exclusions, malformed lines, request files, `--opt=file` rewriting, smuggling through mixed arguments, TLD look-alikes, fuzz keywords, IPv6/mapped addresses, empty targets).

## Accepted risks and limitations

| Risk | Status / mitigation |
|---|---|
| **Single-word arguments** (`intranet`, `dir`, `smb`) cannot be told apart from sub-commands without per-tool knowledge, so they are not scope-checked when they appear as bare arguments. | The preview shows a warning listing them; target files reject them; URLs and `host:port` forms are checked. Use fully-qualified names or IPs. |
| **Indirect inputs not visible on the command line** — configuration files, resume/state files, environment variables, tool-internal crawling, recursion, redirects and template-defined hosts. | Files named in arguments are inspected (a config or resume file that names endpoints is treated as a target list and must be fully in scope). Crawl/recursion behavior is the tool's; keep depth and rate limits conservative. stdin is closed. |
| **Tool features that execute code** (custom scripts, plugins) are part of many security tools. | Every run requires the native OS confirmation showing the full command; there is no shell and no automatic execution. |
| **DNS-based scope**: names are checked, not the addresses they resolve to. Alternative IP spellings as bare arguments (`2130706433`, `127.1`) are not recognised as targets. | Prefer IPs/CIDRs for internal ranges; exclusions still apply by name. Every run still needs the native confirmation, which shows the full command. |
| **Tools that are not target-based scanners** (OpenSSL, hashcat, tshark, Responder and others marked as not needing a scope in the catalog) are not scope-checked, also when an MCP client asks for them. | The MCP approval shows a warning and the native confirmation says that Cyber Hub does not check targets for the tool. Runs requested through MCP still need your approval and the native confirmation. |
| **Working directory:** tools run in Cyber Hub's private `work` folder in app data, so output files given as bare names (`-oN scan.txt`) are written there. | Use absolute paths for output files you want elsewhere. |
| **Windows process trees**: a descendant spawned in the instant before the child is assigned to its Job Object could escape. If the Job Object cannot be attached at all (for example inside a job that forbids nesting), the run output says that cancelling stops only the main process. | Window is microseconds; verified by an automated test that a grandchild is killed. |
| **Very large target files** (> 256 MB) cannot be validated. | They are rejected, not skipped. |
| **Existing history** recorded before redaction was added is not rewritten. | Clear it in Settings → Local data if needed. |
| **Process output** is shown live without redaction (it is ephemeral); stored output is redacted. | Long lines arrive in 16 KB chunks; the stored copy is reassembled per line before redaction, so a secret that spans two chunks is still masked. |
| **Live CVE searches** send the query text to NVD. | Labeled in the UI; a local-cache mode exists. |
| **Resolved addresses of in-scope names (DNS rebinding).** The HTTP request builder, the TLS analyzer and web services checks resolve an in-scope name once and refuse it if any address is private, loopback, link-local, shared (100.64/10) or reserved and not itself in the scope; the request then connects only to those vetted addresses (no second lookup), and a redirect is never followed. Service scans run the same check before starting, but Nmap resolves names again itself, so a name that changes its answer between the check and the scan is not caught. A name that resolves to both a covered and an uncovered internal address (for example `127.0.0.1` and `::1`) is refused as a whole. Refusals are recorded in the project's scope history. | Scope internal ranges by address when they are part of the engagement; for service scans of names you do not control, scan the addresses instead. |
| **The HTTP header analyzer (Security Utilities) is not scope-gated.** It sends one GET or HEAD request (no redirects, body not read) to whatever URL you type, including internal addresses, like a browser would.
