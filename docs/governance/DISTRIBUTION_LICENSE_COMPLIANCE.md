# Distribution license compliance

**Status (Mission 14, 2026-11-13).** What each ExploitX package contains, which license obligations come with distributing it, and how each is met, with the evidence. **This is an engineering record, not legal advice, and it claims no legal compliance.** It records what was built, checked and measured. The questions only a lawyer can settle are listed at the end, and no package built with these changes has been published yet.

## What every package carries: `THIRD_PARTY_LICENSES.txt`

Generated by `node scripts/licenses.mjs notices` ([DEPENDENCY_LICENSE_POLICY.md](DEPENDENCY_LICENSE_POLICY.md)), committed as `src-tauri/resources/THIRD_PARTY_LICENSES.txt`, and installed by every package through Tauri's `bundle.resources`. About 1 MB, it contains:
1. the Rust crates compiled into the Windows or Linux app (the union of both platforms' shipped crates), each with its version, SPDX license and the numbers of its license texts;
2. the npm packages bundled into the interface (runtime dependencies only);
3. the copied code and data (`scripts/license-assets.json`);
4. a statement of the native libraries per package;
5. 333 distinct license and NOTICE texts, verbatim as each package publishes them (Apache-2.0 NOTICE files included); for the nine packages that publish no license file, the standard text of their declared license, marked as such;
6. `THIRD_PARTY_NOTICES.md`: the data catalogs (OWASP, MITRE ATT&CK, FIRST CVSS), fonts, icons, copied components and the Windows installer toolchain.

It also says where the source is: every crate at its version on crates.io, compiled unmodified (MPL-2.0 §3.2 for `cssparser`, `dtoa-short`, `option-ext` and `selectors`); every npm package on the npm registry, with the install-time patches named in `scripts/patch-deps.mjs`.

Settings > About shows the installed file's path, with a link to `THIRD_PARTY_NOTICES.md` online.

## Windows installers

* **No third-party native library is bundled.** WebView2 is not redistributed: the installers download and run Microsoft's WebView2 bootstrapper only when WebView2 is missing (the MSI's `DownloadAndInvokeBootstrapper` action; neither installer contains the bootstrapper).
* **Installer toolchain code inside the installers:**
  * the NSIS installer carries NSIS's runtime with the LZMA decompressor and the plug-ins System, nsDialogs, StartMenu and NSISdl (zlib/libpng license; the LZMA module is under CPL-1.0, with an exception that keeps code linked to it outside the CPL), plus Tauri's `nsis_tauri_utils` plug-in (MIT OR Apache-2.0);
  * the MSI carries WiX 3.14.1's user-interface custom action (`WixUIWixca`) and its dialog images (MS-RL). The WiX project states that "the installer packages generated by WiX will normally fall outside the scope of the MS-RL".
  * Both licenses, verbatim as distributed with the tools, and the tools' source locations are in `THIRD_PARTY_NOTICES.md` (and so in every package).
* **Evidence:** the MSI's `Binary` table holds `WixUIWixca` and six `WixUI_*` images; its custom actions are `LaunchApplication`, `WixUIValidatePath`, `WixUIPrintEula`, `DownloadAndInvokeBootstrapper` and two property setters (read from the second release candidate's MSI with the Windows Installer API, read-only).

## deb and rpm

They install `/usr/bin/cyber-hub`, `/usr/bin/cyberhub-mcp`, the desktop entry, icons and the notices, and depend on the distribution's `libwebkit2gtk-4.1-0`, `libgtk-3-0` and related packages. Those libraries are not redistributed by ExploitX: the user's distribution supplies them with its own notices and sources.

## AppImage

The AppImage is the one package that redistributes LGPL and GPL code. Its bundler (linuxdeploy) copies GTK, WebKitGTK and their whole dependency tree from the build machine (the release workflow's `ubuntu-22.04` runner), dynamically linked, into `usr/lib/`.

### What the second release candidate's AppImage contains (measured)

Unpacked in `ubuntu:22.04` and mapped to Debian packages with `dpkg -S`:
* **170 shared objects from 108 Ubuntu 22.04 packages.** No glibc, `libstdc++` or `libgcc` (the AppImage excludelist leaves them to the host). The app binary links them dynamically.
* Licenses, from the packages' copyright files: mostly **LGPL-2.0/2.1/3.0-or-later** (WebKitGTK, JavaScriptCore, GTK 3, GLib, GStreamer, libsoup, GnuTLS, Nettle, Pango, cairo, libsecret, Avahi, systemd's libraries…), permissive licenses (ICU, libxml2, libpng, libjpeg, libwebp, SQLite, HarfBuzz, libffi, FreeType…), Apache-2.0 (CUPS), and **`libjbig0` (jbigkit): GPL-2.0-or-later**, loaded through libtiff by GDK-Pixbuf's TIFF loader.
* linuxdeploy had copied **98** copyright files into `usr/share/doc/`. **10 packages had none:** dconf-gsettings-backend, glib-networking, libbz2-1.0, libcap2, libdbus-1-3, libkeyutils1, liblzma5, libpcre3, librsvg2-common, libselinux1.
* **No source was published or offered.** This is the gap Mission 12 recorded.

### What the release now does (`scripts/appimage-licenses.sh`, release workflow)

Before `tauri build`, on the Linux build runner:
1. **Collects** the dependency closure of the libraries the bundler starts from: WebKitGTK, JavaScriptCore, GTK 3, librsvg, Ayatana AppIndicator, GTK's input-method and print modules, GDK-Pixbuf loaders, GIO modules and WebKit's helper processes. It maps them to their Debian packages, then copies:
   * each package's **copyright file** into `copyright/<package>`;
   * the **license texts** those files refer to (`/usr/share/common-licenses/`: GPL-1/2/3, LGPL-2/2.1/3, Apache-2.0, MPL-1.1/2.0, BSD, Artistic, GFDL, CC0) into `common-licenses/`.

   It also writes `PACKAGES.tsv` (package, version, source package, source version, licenses) and `README.txt` (dynamic linking, where the source is, how to replace a library).
2. **Downloads the Debian source packages** (`.dsc`, upstream and Debian tarballs, via `apt-get source` from `archive.ubuntu.com` and `security.ubuntu.com`) of every library whose copyright file names the GNU GPL or LGPL, including free-form copyright files that name them only in their text. They go into `ExploitX-AppImage-library-sources_<version>.tar`, which the release publishes next to the AppImage. That asset is covered by `SHA256SUMS.txt`; it is not an update artifact, so it is not update-signed.
3. **Puts the collected folder into the AppImage** at `usr/share/doc/exploitx-appimage/` (a generated `bundle.linux.appimage.files` configuration, passed to `tauri build`).
4. After the build, **checks the AppImage** (`node scripts/check-package-notices.mjs`, which runs `appimage-licenses.sh --check`):
   * every shared library under `usr/lib/` must map to a package whose copyright file is in the AppImage, or the release stops;
   * the source archive must contain Debian source packages.

### How this maps to the licenses (engineering reading, not legal advice)

* **LGPL-2.1 §6 / LGPL-3.0 §4, GPL-2.0 §3, GPL-3.0 §6:** the object code is accompanied by the complete corresponding source. Offering it "from the same place", the release page that offers the AppImage, is the form GPL-2.0 §3 (last paragraph), LGPL-2.1 §6(d) and GPL-3.0 §6(d) describe. No written offer is made: a written offer would be a commitment the owner makes for three years, and is not needed when the source accompanies the binaries.
* **License texts (GPL §1, LGPL §1):** each library's copyright file and the full texts they refer to are inside the AppImage.
* **Replacing the LGPL libraries:** they are separate shared libraries. `README.txt` explains how to extract the AppImage (`--appimage-extract`) and replace one, or use `LD_LIBRARY_PATH`.
* **Permissive libraries:** their copyright and license notices are in the copyright files.

## Legal review and owner decisions

These are open. They are not resolved by engineering:

1. **`libjbig` (GPL-2.0-or-later).** It is a dependency of libtiff, which GDK-Pixbuf's TIFF loader uses; ExploitX never calls it directly. Whether distributing it in the AppImage beside ExploitX creates a "work based on the Program" that must be under the GPL is a legal question. The source is now published either way. **Engineering alternative:** leave the TIFF loader out of the AppImage (ExploitX does not need TIFF images in its interface), which removes `libtiff` and `libjbig`; this changes the AppImage and needs a test build. **Owner decision; legal advice recommended.**
2. **The first real release run.** The collection, the source download and the checks were run in containers and in local builds, not yet in the release workflow on GitHub's runner. The next release candidate is the first: confirm that its draft has the source archive and that the AppImage contains `usr/share/doc/exploitx-appimage/`.
3. **Distribution mirrors.** The release downloads the source from `archive.ubuntu.com` at the versions the runner has installed. If a version had just been superseded there, the download fails and the release stops (it does not ship an AppImage without its source).
4. **Source availability period.** The source archive stays on the release page as long as the release does. Deleting a release that has an AppImage would also remove its source; keep both, or move the release's AppImage and source together.
5. **The WiX statement and the CPL-licensed LZMA module** are quoted, not legally reviewed. Their licenses and source locations are shipped to stay on the conservative side.
6. **Alternative for the owner:** ship only the deb and rpm for Linux, with no AppImage, and none of the library obligations apply.

## Keeping it this way

* Never add a native library to the Windows, deb or rpm packages without adding its notice to `THIRD_PARTY_NOTICES.md` (it then reaches every package).
* When the release runner's image changes (for example to Ubuntu 24.04), rerun the collector in that image and compare: `bash scripts/appimage-licenses.sh <dir>` then `--check` on an extracted AppImage.
* Keep `node scripts/check-package-notices.mjs` in the release workflow; `src-tauri/src/ci_tests.rs` pins it.
